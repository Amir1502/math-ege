# Запуск и границы развёртывания

## Назначение среды

Эта поставка предназначена для локальной разработки и закрытой проверки первого этапа. GitHub содержит исходный код, а не размещённое публичное приложение. Развёртывание для учеников требует независимой предметной проверки, юридического режима обработки данных и выполнения оставшихся FR/NFR из ТЗ.

Сервис `web` слушает только `127.0.0.1:8080`. База и API не публикуют порты на компьютере. Сеть базы внутренняя. Данные PostgreSQL сохраняются в именованном томе `postgres_data`.

## Docker Compose

Нужны Docker Engine с Compose v2 и доступ к Docker Hub.

1. Скопировать `.env.example` в `.env`.
2. Записать в `POSTGRES_PASSWORD` случайный пароль из 64 шестнадцатеричных символов. Такой алфавит безопасен внутри URL базы и YAML-интерполяции. Пароль не публиковать и не добавлять в git.
3. Сохранить `APP_ORIGIN=http://127.0.0.1:8080` и открывать интерфейс именно по этому адресу. Если нужен другой origin, изменить его до запуска.
4. Для демонстрационного набора оставить `ALLOW_DEMO_CONTENT=true`. При `false` сервер не выдаёт непроверенные задачи.
5. Выполнить:

```sh
docker compose up --build -d
docker compose ps
```

Интерфейс: `http://127.0.0.1:8080`. OpenAPI JSON: `http://127.0.0.1:8080/api/openapi.json`. Для разработки интерактивная документация FastAPI доступна непосредственно на локальном API `http://127.0.0.1:8000/docs`.

После изменения моделей требуется новая миграция; приложение не должно пересоздавать таблицы вместо неё. Контейнер API запускает `alembic upgrade head` перед сервером.

Для остановки без удаления данных:

```sh
docker compose stop
```

Не выполняйте команды удаления томов без подтверждённой резервной копии и осознанного согласия на потерю данных. Остановка сервиса и удаление его данных имеют разные последствия.

## HTTPS и публичный запуск

Публичный запуск в этой поставке не настроен. Для него нужны TLS-прокси, собственный домен, `COOKIE_SECURE=true`, точный `ALLOWED_ORIGINS` и утверждённая политика данных. Нельзя открывать PostgreSQL наружу или оставлять гостевые куки без Secure в публичной HTTPS-среде.

Контейнеры API и web непривилегированные, с файловой системой только для чтения, временным `tmpfs`, `cap_drop: ALL` и `no-new-privileges`. Версии базовых образов закреплены digest. Их обновление выполняется отдельным изменением после тестов и проверки уведомлений безопасности.

nginx использует shared-zone upstream с `resolve` и Docker DNS `127.0.0.11`. После замены контейнера API его адрес переопределяется без ручного перезапуска web. Ответы шлюза 413, 429, 502 и 504 имеют ту же JSON-оболочку ошибки, что API. Это не заменяет клиентское сохранение черновика при недоступной сети.

## Обновление клиента и PWA

В dev-режиме service worker отключён. Для локальной проверки PWA сначала выполнить `npm run build`, затем `npm run preview -- --port 5173 --strictPort` из `frontend/` при работающем API с этим origin. Сквозные тесты выполняют эти шаги автоматически и не используют уже запущенный сервер.

PWA использует `registerType: 'prompt'`, `skipWaiting: false` и `clientsClaim: false`. Новая версия ожидает подтверждения; на экране активной задачи кнопка обновления не предлагается. Проверяется также локально сохранённое активное занятие перед вызовом обновления. Приватные API не помещаются в CacheStorage; открытые уроки и черновики сохраняются в IndexedDB, последние изменения черновика и ожидающей операции дополнительно журналируются в `localStorage`.

**Ожидание service worker не сохраняет старые файлы на сервере.** На первом посещении вкладка может ещё не управляться worker. Если заменить `dist` под работающим preview, она может запросить уже удалённый хешированный модуль и получить 404. Такой сбой динамического импорта воспроизведён при проверке; после перезагрузки завершённое занятие восстановилось. Автоматическую принудительную перезагрузку во время ответа приложение не запускает.

Для локального обновления завершить занятие, убедиться в серверном сохранении, закрыть проверочные вкладки, остановить preview, собрать клиент заново и снова запустить preview. Затем открыть приложение и при необходимости подтвердить обновление. Не очищать cookie или IndexedDB как способ обновления: это может лишить гостя доступа к истории.

Для непрерывного публичного развёртывания нужны атомарное переключение версии и сохранение старых хешированных ресурсов на период жизни открытых вкладок, проверка нескольких вкладок и отката. В этой поставке такая система выпуска не реализована; простая замена web-контейнера не доказывает безопасное обновление активных клиентов.

## Что ещё не проверено этой поставкой

- Нагрузка 500 активных пользователей и 30 API-запросов в секунду.
- RPO 24 часа, RTO 4 часа, автоматическая резервная копия и восстановление.
- Работа с несовершеннолетними, 152-ФЗ и размещение российской базы.
- Межустройственное объединение аккаунта, одноразовые ссылки и MFA администратора.
- Производственное серверное время пробника и сценарии разрыва связи пробника.
- Смена версии клиента с сохранением старых ресурсов, несколькими вкладками и откатом.

Эти пункты не заменяются успешной локальной сборкой.
