# Защитные границы первого этапа

## Что хранится

Гостевая cookie содержит случайный секрет доступа к анонимной истории. Cookie HttpOnly и SameSite=Strict; в HTTPS-среде обязателен Secure. В базе хранится хеш, не исходный токен. Очистка cookie может лишить доступа к серверной гостевой истории; отдельного восстановления гостевого доступа на этом этапе нет. Черновики и ожидающая отправки операция дополнительно находятся в IndexedDB текущего origin. Синхронный журнал в `localStorage` сохраняет последние изменения черновика и ожидающей операции перед перезагрузкой; гостевой токен в него не записывается. Очистка данных сайта может удалить обе локальные копии.

В эту версию не входят email, телефон, имя, школа, дата рождения, публичные профили, реклама и внешняя аналитика. Гостевой токен и его хеш не включаются в JSON-выгрузку.

## Границы доверия

1. Браузер → API: все JSON-поля, значения заголовков, ответы и время решения проверяются на сервере. Клиентское время не является доказательством экзаменационной честности.
2. Гость → сессия: на каждом закрытом маршруте проверяется владелец. Наличие случайного ID сессии не заменяет проверку доступа.
3. Контент → интерфейс: поля условия выдаются белым списком. Эталон, полное решение и текст подсказок не входят в ответ условия. Произвольные HTML, JavaScript и SVG не выполняются.
4. API → база: SQLAlchemy использует параметры запросов; текст ответа не становится частью SQL.
5. CI → GitHub: workflow имеет только `contents: read`, не принимает production-секреты, не запускает ИИ-агента и не использует привилегированный `pull_request_target`.

Все изменяющие браузерные операции требуют собственного заголовка и допустимого Origin. Открытый CORS не используется. Ключи идемпотентности связываются с пользователем, действием и телом запроса. Лимиты исходного ответа и тела запроса предотвращают неограниченную обработку входа.

## CI: проверенные факты

Workflow: `.github/workflows/ci.yml`.

- Триггеры: push в `main`, pull_request.
- Кто вызывает: пользователи с правом push, авторы разрешённых pull request. Код pull request считается недоверенным.
- Разрешения: `contents: read`, остальные не назначены.
- Секреты: пользовательские секреты не используются; PostgreSQL-пароль случайный и временный, создаётся в job и маскируется.
- Недоверенные значения: `github.ref` влияет только на группу concurrency, не подставляется в shell-команду.
- ИИ-агент: отсутствует.
- Checkout не сохраняет учётные данные. Все actions закреплены полным SHA, полученным из официальных репозиториев.

Статическая проверка workflow выполняется actionlint и viora-aegis. Наличие проверки не подменяет подтверждение результатов в `docs/verification.md`.

Проверены используемые SHA, входные параметры и границы workflow. Полный исходный код `actions/checkout`, `actions/setup-python`, `actions/setup-node` и `actions/upload-artifact` не аудировался. Reusable workflows в этой конфигурации не вызываются.

## Разобранные сигналы статического анализа

Финальный staged-scan и разбор `XSS-002`, двух `AUTH-005` и `DEFAULT-109`: [`security-review.md`](security-review.md). Сырой exit 1 сканера сохранён как факт; ложные срабатывания не выдаются за подтверждённые уязвимости и не скрываются подавлением правил.

`DEFAULT-109`, привязка Uvicorn к `0.0.0.0` в `backend/Dockerfile`: не является открытым внешним API в поставляемой конфигурации. В `compose.yaml` у API нет `ports`, маршрут доступен только nginx во внутренней сети приложения. Привязка к loopback внутри контейнера заблокировала бы nginx. Для запуска без контейнера README использует `127.0.0.1`. Этот вывод относится только к данной Compose-конфигурации; публикация порта API отдельной командой меняет границу доступа.

При отдельном просмотре инфраструктуры исправлены три дефекта: динамическое разрешение имени контейнера API через Docker DNS вместо сохранения старого IP, JSON-ответы для сбоев шлюза 502/504, исключение `.env` на любой глубине Docker build context. Статический тест `scripts/verify-infra.mjs` фиксирует эти ограничения. Он не доказывает поведение DNS или тайм-аута в работающем контейнере; это отдельная runtime-проверка.

## Ограничения

Полный npm-аудит не чистый: известны 15 затронутых dev-пакетов уровня low/moderate, сведённые к трём уведомлениям. Версии, цепочки и границы оценки перечислены в `docs/dependencies.md`. Чистый production-only npm-аудит и проверка установленного Python-окружения не заменяют аудит сборочной цепочки и базовых образов.

Это не полный аудит безопасности и не разрешение публичного запуска. До публичной версии нужны: юридические согласия, срок удаления гостевых данных, облачный аккаунт, серверная авторизация ролей, MFA методиста/администратора, TLS, резервные копии и тест восстановления, мониторинг и нагрузочная проверка.

Не выполнялись атаки на сторонние сервисы. Не оценивались производственный домен, облачная инфраструктура, политика обработки несовершеннолетних и реальное восстановление PostgreSQL. Предметная корректность не заменяется технической проверкой схемы контента.
